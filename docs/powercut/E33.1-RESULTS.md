**Head SHA:** `c6288f4cf7d78d47f270e60cc3932e26b86e189f` (branch `e33-ntfs-i30-log-attribution`)
**Artifacts:** `e33-artifacts-45297618762` (per-arm ETL + CSV, raw `$MFT`/`$LogFile` images,
`decoded-index-records.{json,csv}`, `target-page-writes.csv`, `l3-attribution.json`,
`E33-evidence.json`, `open-probes.{json,csv}`, `fixture-residency.json`, `volume-info.json`,

**Environment:** Windows Server 2025, build 26100, `windows-latest`; volume `D:` NTFS,

**Supersedes:** the E33 numbers in [E33-RESULTS.md](E33-RESULTS.md) (commit `9c8eb27`), which
were produced by a hand-rolled local analysis and are superseded by this run.

E33 asked which handle/API makes the exact `$LogFile` redo/undo records of a test
directory's `$I30` reach the storage device behind a flush barrier. E33.1 closes the
evidence chain: the decoded records are now attributable to the tested file *and* its
parent directory, the target log pages are matched by physical offset rather than by
proximity, and every barrier is correlated to the candidate API call that produced it.

## 2. Open handles (unchanged conclusion, now measured in CI)

The explicit `$I30:$INDEX_ALLOCATION` stream handle opens only with
`FILE_FLAG_BACKUP_SEMANTICS`:

| Path | without backup semantics | with backup semantics |
|---|---|---|
| `D:\e33\small:$I30:$INDEX_ALLOCATION` | `ERROR_ACCESS_DENIED` (5) | opens (`GENERIC_READ\|GENERIC_WRITE` and `FILE_READ_DATA\|FILE_WRITE_DATA`) |
| `D:\e33\small::$I30:$INDEX_ALLOCATION` | `ERROR_ACCESS_DENIED` (5) | opens |
| `D:\e33\small:$I30` | `ERROR_FILE_NOT_FOUND` (2) | `ERROR_FILE_NOT_FOUND` (2) — `$INDEX_ROOT` is not separately openable |
| `D:\$LogFile`, `D:\$MFT` | `ERROR_ACCESS_DENIED` (5) | not openable by name even as admin |
| `D:\` root, `\\.\D:` | open | open |

`NtCreateFile` on the stream paths returns `0xC000003B`
(`STATUS_OBJECT_PATH_SYNTAX_BAD`): the Win32 path normalizer is required for the
`:$I30:$INDEX_ALLOCATION` syntax. Full matrix in `open-probes.csv`.

## 3. Decoded index records (Task 1)

`decoded-index-records.csv` carries one row per decoded index operation, matched to the
arm's own `e33_<ARM>_*` file names and to the test directory's MFT record. Each row
keeps the LSN, transaction id, redo/undo opcodes, index type (resident/non-resident),
child and parent MFT references, and the raw record location (log page, record offset,
page byte offset) plus the LSN-derived page for comparison.

Every arm decoded 105–120 of its own index operations (add + delete):

| arm | A | B | C | D | E | F | G | H | I | J | K | L | M | N | O |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| decoded index records | 120 | 112 | 108 | 118 | 115 | 105 | 106 | 114 | 112 | 109 | 116 | 108 | 109 | 113 | 114 |

The decoder orders records by LSN (not by physical page order, which is not chronological
in a circular log) before rebuilding the open-attribute table, and preserves the raw
offsets. The decoder is validated against a real 64 MiB `$LogFile` independently
(409,685 records; `AddIndexEntryRoot`, `AddIndexEntryAllocation`,
`DeleteIndexEntryAllocation`, `UpdateFileNameAllocation` all decode) and has a
synthetic round-trip selftest (`--selftest`).

## 4. Target-page writes (Task 2)

`target-page-writes.csv` lists every ETW write that landed on an RCRD page holding a
target index record, with the required columns (arm, operation, filename, lsn,
transaction_id, rcrd_page, stream_offset, physical_byte_offset, write_timestamp,
write_size). The mapping is arithmetic, not a heuristic:

```
device ByteOffset -> volume offset   = ByteOffset - partition_offset   (measured: 16777216)
volume offset     -> $LogFile offset  = offset - logfile_lcn * cluster  (from $MFT record 2)
$LogFile offset   -> RCRD page        = offset // 4096
```

Writes to the `$LogFile` that carry *other* records are excluded: across all 15 arms,
805 writes landed in the `$LogFile` extent and 0 of the 855 target-page rows carry a
foreign arm's file name. Arm A, J and L — the three arms whose flush never issued a
successful flush — show **zero** `$LogFile` writes at all.

## 5. Barrier attribution (Task 3)

`l3-attribution.json` has one entry per candidate call (900 = 15 arms × 20 reps × 3
operations). A call is L3 only when all of these hold:

1. an index record exists for that call's file, with the test directory as parent;
2. a `DiskIo/Write` event landed on that record's page **inside the call's window**
   (`OperationStart … CandidateFlushEnd`);
3. a `FlushInit`/`FlushBuffers` pair with the **same IRP** brackets that write
   (`write ≤ FlushInit ≤ FlushBuffers`);
4. that barrier completed **before** the candidate API returned
   (`FlushBuffers ≤ CandidateFlushEnd`);
5. the API returned success;
6. the barrier's `IssuingThreadId` matches the calling thread (rules out background
   flushes).

Measured margins: write → barrier start 7.8–46.4 µs; barrier completion → API return
52.8–7340.6 µs. No barrier that completed after the API returned was counted, and no
call with an in-window target write failed to find a covering barrier.

## 6. Results

`Target index records` = decoded operations for that arm's own files.
`Target pages written` = ETW writes landing on those pages.
`Barrier before API return` = candidate calls with a correlated barrier.

|---|---:|---:|---:|---|---|
| none → no flush (A) | 120 | 0 | 0 | 0 | **L1** |

| parent dir → `FlushFileBuffers` (C) | 108 | 61 | 9/60 | 0 | **L3** |

| `$I30` stream (small dir) → `FlushFileBuffers` (O) | 114 | 78 | 8/60 | 0 | **L3** |

**Which APIs genuinely achieve L3:** every arm whose flush call actually succeeded and
issued a flush — B, C, D, E, F, G, H, I, K, M, N, O. The three arms that reach only
L1 are the ones where no flush was issued at all: A (by design), J (the `$LogFile`
handle cannot be opened), L (the volume-device handle cannot be flushed). The volume
root (K) is a control, not a production recommendation — the E26 withdrawal stands.

**No arm reaches L4.** No write to the fixture directory's `$MFT` record cluster or to
its `$INDEX_ALLOCATION` extents was observed inside a measured window, so the index
*home page* is still not made durable by any of these flushes. This agrees with
E17's home-page finding and does not contradict it: E33.1 shows the *log records* are
flushed, not the index pages themselves.

### Same-topology comparison (Task 5)

C/D/E (parent directory) and F/G/H/I (`$I30` stream) now run against the **same** large
directory, whose `$I30` is non-resident (`i30_nonresident=true`, 512 KiB
`$INDEX_ALLOCATION`, verified from the `$MFT` record):

| Handle on the large directory | Target pages written | Barriers before API return |
|---|---:|---:|
| parent directory (C/D/E) | 61 / 80 / 74 | 9 / 14 / 10 |
| `$I30` stream (F/G/H) | 56 / 52 / 73 | 7 / 9 / 5 |

The two handles are indistinguishable at this level: both flush the target log pages
behind barriers, and neither writes the index home page. M/N/O keep the small
(resident-index) comparison, where the same picture holds (77 / 72 / 78 target pages,
13 / 7 / 8 barriers).

## 7. Honest limits

- **Per-call L3 is the minority, and that is the result.** 119 of 900 calls carry a
  barrier. The reason is measurable, not a gap in the attribution: an arm performs 60
  namespace operations, but the `$LogFile` pages that hold their index records are
  written in bursts of ~64 page writes spread across the arm, and a given call's page
  is only written when NTFS happens to write it inside that call's sub-millisecond
  window. The remaining calls are L1: their index record exists and was decoded, but
  its page was not written inside the call's own window (the write landed outside it,
  or the page was written by a neighbouring call's flush).
- The delete target file is recreated under the same name each rep, so its index
  records repeat; those 81 of the 119 L3 calls are disambiguated by the *window*, not
  by the name. Verified: every covered write for a shared-name call falls inside that
  call's own window (0 exceptions).
- `$LogFile` snapshots are taken after the arm's window, and the log is circular: for
  the busiest arms only 13–18 of the 20 created names are still present in the
  snapshot (older records were overwritten). The decode therefore covers a suffix of
  each arm's history, not its whole history.
- The barrier's `IssuingThreadId` match is the strongest available discriminator
  between the candidate's flush and a background flush; ETW does not expose an IRP
  completion event for the flush path on this build, so "matching IRP completion" is
  established by the `FlushInit`/`FlushBuffers` IRP pairing rather than by a separate
  completion event.
- The rig's own ETW marker provider did not survive the tracer change: the custom WPR
  profile was rejected (no DiskIo events), so the recorded sessions carry no marker
  events. The correlation does not need them — the rig records FILETIME boundaries,
  which is the same base as the ETW `Clock-Time` column — but the marker channel
  (`E33Marker.cs`, `e33-profile.wprp`) is currently unused and is reported as such.
- **L5 is untested.** Nothing here says the namespace change survives a power cut; that
  needs the Tier-2 QEMU/`blklogwrites` rig.

## 9. Reproducing from the artifact

The artifact alone is enough to regenerate every table above:

```
gh run download 45297618762 -R takomitkm/leveldb -D out
python docs/powercut/e33/e33_etw_analyze.py --etw-dir out/.../etw \
    --out out/.../etw-summary.json --csv out/.../etw-summary.csv
python docs/powercut/e33/e33_integrate.py --artifacts out/.../e33-artifacts-*
```

`e33_integrate.py` reads the ETL-derived CSV, the extracted `$MFT`/`$LogFile` images and
`volume-info.json`, and rewrites `decoded-index-records.*`, `target-page-writes.csv`,
`l3-attribution.json` and `E33-evidence.json`. The same command run on this artifact
reproduced the numbers in §3–§6 exactly.
