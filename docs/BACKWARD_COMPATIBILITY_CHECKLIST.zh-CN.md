## 2. 判断标准和取舍

### 2.1 什么才算要修的“不兼容”

- **必须修复：**原来符合公开契约的有效输入，现在漏数据、读错库、错误成功、不能正常调用；交付包不完整；在宣称支持的组合里无法编译/链接/运行。
- **应由库默认兼容：**作为上游替代品时，原有路径参数含义、正常数据库读写、自定义 Env 的既有合法实现，不宜要求所有旧调用方改代码。
- **限定范围兼容：**ABI、CRT、工具链、压缩能力、文件系统和权限必须明确支持范围。无法保证任意组合都互换，可以提供不同包或要求匹配构建。
- **不应为兼容而恢复：**越界访问、把不完整日志继续当成可安全追加、丢弃有效返回缓冲区、虚报成功。这些历史缺陷不构成应保留的行为。
- **可记录后接受：**损坏输入更早报错、恢复后文件号变化、日志轮换与时钟分辨率变化等，前提是没有打破公开保证或丢失合法数据。
- **尚待测：**有机制上的可能性，但没有对照证据。不能直接写成“有 bug”，也不能凭单次成功写“完全兼容”。

“必要性高/中/低”指是否值得为下游做兼容工作，不等同于漏洞严重度。每项应填写“修复 / 限定支持 / 保留新行为 / 只补文档”之一，并写明理由。

### 2.2 不要用错误的验收目标

1. 能编译不等于 ABI 兼容；能加载不等于 C++ 对象跨 DLL 边界安全。
2. `DB::Open().ok()` 不等于数据完整；必须检查所有键值、迭代顺序和恢复后的再次读写。
3. 压缩选项设成 Zstd 不等于实际生成 Zstd 块；必须确认落盘块类型和解码路径。
4. CTest 返回 0 不等于执行了测试；必须检查命中数量、跳过数和 XML 报告。
5. 进程强杀不等于断电；重命名后立刻读到数据也不等于已经能抵抗物理掉电。
6. 一次损坏后的修复结果不能代表正常数据格式兼容，也不能当成无损恢复承诺。
7. U 与 C 同时失败时先排环境与基线缺陷；不能只看 C 红了便归因给 fork。

## 3. 执行前的准备

### 3.1 目录和环境

构建、依赖安装和重型测试放校机；本机只维护文档、源码及轻量检查。建立一套独立实验目录，例如：

```text
D:/yzd/leveldb-compat/
  runner/                  自己审过的调度脚本，从这里启动
  sources/U/               固定上游源码，只用于对应实验
  sources/F0/              历史坏版本，用来确认测试能抓到问题
  sources/F1/              当前基线
  sources/C-ACP/           候选 ACP 独立工作副本
  sources/C-UTF8/          候选 UTF-8 独立工作副本
  builds/                  每种模式独立构建目录
  installs/                每种模式独立安装目录
  fixtures/pristine/       原始夹具，只读保留
  fixtures/runs/           每次试验用一份新副本
  packages/                每份下载/解压资产各自一个新空目录
  evidence/                命令、日志、XML、哈希、结论
```

不要在同一数据库上轮流做多个破坏性实验。损坏、Repair、强杀、ACL、物理断电测试都用不同副本。数据库要完全关闭后再做普通文件复制；不能把随手复制的正在写入目录当成可信备份。

自写脚本与下载/解压目录分开，Python 使用 `-I`。所有执行串行，尤其 `tools/check_compatibility.py` 会临时修改源码并重建，不能与别的构建共享同一份源码。

### 3.2 先做分层矩阵，不要一开始跑所有排列

| 层 | 第一轮最小组合 | 通过后再增加 |
| --- | --- | --- |
| 工具链 | Windows x64 MSVC，Linux x64 GCC | 项目实际要支持的 MinGW、Clang、ARM64/32 位及其他系统 |
| 构建 | Release，默认异常/RTTI；静态库与 DLL 各一份 | Debug；异常/RTTI 协调关闭；下游真实 flags |
| 路径 | ACP 936 + ACP 构建；同环境 UTF-8 构建 | ACP 1252、系统 UTF-8 代码页、OEM 文件 API 模式 |
| 文件系统 | 本地 NTFS 普通可写目录 | 受限 ACL、UNC/SMB、ReFS/exFAT、重定向目录等实际部署 |
| 数据 | 正常关闭的无压缩库；真实 Snappy 压缩库 | 真实 Zstd、WAL 恢复、MANIFEST 恢复、损坏夹具 |

| 交付 | 从干净源码构建安装 | 实际下载包解压后消费者；升级、降级、回滚 |

不支持的矩阵格可以明确排除，但不能填写“通过”。不必兼容所有古老系统或编译器；先列出项目打算承诺的最低版本。

### 3.3 数据夹具

准备确定性数据清单，并保留库外的期望值。建议至少包含：空 key、空 value、嵌入 NUL 的二进制 key/value、UTF-8 中文内容、共同前缀、覆盖写、删除与重新插入、跨多个 block 的大 value、批量写和 snapshot。

为清洁关闭测试准备约 10,000 个可重建键值；为 codec 测试另准备高度重复的数据与足够大的 SST。数量是测试输入，不是库的性能承诺。每份夹具标记：生成程序版本、库 SHA、编译器、压缩设置、比较器名、写入/关闭方式、文件清单与 SHA-256。

恢复夹具必须由真实 DB 写入有效 WriteBatch。以前日志组件探针中的任意文本 record 只能验证 Reader，不能直接塞进 WAL 当成完整 DB 恢复夹具。

## 4. 逐项清单：身份、接口、构建和交付

### BC-01 固定源码、发布包和运行库身份

- [ ] **目标/必要性：高，先做。** 不兼容判断必须对应实际运行的那份库。
- **为什么会误判：**main、分支、tag、preview 和本地 DLL 可能不是一个 SHA；PATH 或工作目录可能加载另一份旧 DLL；旧 CMakeCache 可能保留另一个模式。
- **怎么测：**①分别记录 U/F1/C 完整 SHA 和干净状态；②tag 解析到 commit，区分 tag 对象；③核对包哈希、BUILD-INFO 和构建记录；④记录程序实际加载的 DLL 绝对路径或 Linux shared-object 路径；⑤比较两套 PATH 和 build cache；⑥从空 build 目录重做最小消费者。
- **怎么判断：**身份不同先停止后续比较，不能写“同版不稳定”。源码构建、原包、重新打包件分别留记录。
- **怎么修：**固定 ref、独立 build/install、明确加载路径，消除误加载；发布流水线禁止混用其他 SHA 的 preview。
- **验收/边界：**所有后续证据都能追溯同一组身份；本项不证明功能兼容。

### BC-02 公共 API 与源码兼容

- [ ] **目标/必要性：高，默认应兼容上游合法调用。**
- **状态/原因：**旧审查公开头仅注释有变，不代表以后不会改；也不能仅比较几个常用函数。
- **怎么测：**①比较 U 与 C 全部公开头，包括 C API、export 宏和条件编译；②用旧头编译覆盖 DB、Options、Status、Slice、WriteBatch、Iterator、Cache、Comparator、FilterPolicy、Env 的独立消费者；③再换 C 的头重编同一源码；④覆盖自定义派生类和 EnvWrapper；⑤C 编译器单独编译 `c.h` 消费者；⑥按承诺的 C++ 标准验证，至少核对项目要求的 C++17，不能暗中引入 C++20。
- **预期：**相同受支持配置下无需改下游源码；合法覆盖函数不会因参数、const、虚函数或布局变化失败。
- **怎么修：**保留原声明和默认值；新增能力优先采用不打破现有调用的明确扩展。必须破坏时明确版本边界和迁移方案。
- **是否值得：**值得；但不必把下游对私有内部头的依赖自动升级成公共承诺，先列明它使用了哪些非公开接口。

### BC-03 真正的二进制替换，而非重新编译成功

- [ ] **目标/必要性：高，但只对声明支持的 ABI 组合承诺。**
- **原因：**导出符号、虚表/typeinfo、调用约定、类布局、STL ABI、架构和运行库都可能影响旧程序；静态 `.lib/.a` 的替换本来就需要重新链接，不属于只换 DLL。
- **怎么测：**①固定同一 MSVC/架构/CRT/配置，使用 U 的头和 import library 编译旧消费者；②保留可执行文件不重新编译/链接；③仅在隔离运行目录替换成 C 的 DLL，并核对实际加载路径；④覆盖正常读写、迭代、异常路径、构造/析构、Env 派生类、typeinfo；⑤比较导出符号及 Windows import library 或 ELF SONAME；⑥另列静态库重新链接测试。
- **预期：**在明确承诺的组合里旧二进制完整运行，不能只用 LoadLibrary 成功作为结论。
- **怎么修：**维持符号/ABI，或者明确不承诺旧二进制替换，提供源码重编包；必要时用版本化库名避免静默覆盖。
- **不必兼容：**MSVC 与 MinGW C++ ABI、x86 与 x64、任意编译器版本互换。应给出清楚错误和选择指引，而非伪装通用包。

### BC-04 MSVC DLL、CRT 与跨模块 C++ 对象

- [ ] **目标/必要性：高，DLL 交付的重点。** F1 已有 f11fe16 相关修正；须以实际编译命令和包元数据复核，不沿用“所有 MSVC 包一律 /MT”的旧说法。
- **原因：**库内分配、调用方析构的 `std::string`、Status、对象和错误路径可能跨 CRT；Debug/Release 和 iterator-debugging 也可能不匹配。某些组合暂时不崩不能证明安全。
- **怎么测：**①建立 DLL/消费者运行库匹配的 Release 与 Debug 正例；②独立设置 `/MD`、`/MDd`、`/MT`、`/MTd`，先列出支持和应拒绝的组合；③读取编译/链接命令并核对 BUILD-INFO；④循环创建、关闭 DB，读取长 value、构造长错误消息、跨模块释放返回对象；⑤用可用的内存检查工具运行；⑥在干净进程中测每组，记录 LNK2038、加载错误或运行异常。
- **预期：**支持组合没有堆错误；不支持组合在构建或说明上明确拒绝；不能通过忽略 `/NODEFAULTLIB` 等链接警告强行算通过。
- **怎么修：**DLL 与消费者协调使用共享运行库；静态包明确自己的 CRT。必要时降低跨边界 STL 依赖，但这属于接口设计，不能临时强改公共 ABI。
- **取舍：**值得支持常见正确组合；不值得保证任意 CRT 混用。`/MT` 规避宿主旧 DLL 的历史测试收益，不等于适合所有 DLL 消费者。

### BC-05 C API 的内存所有权和回调

- [ ] **目标/必要性：高，尤其给 Python/其他语言绑定或 DLL 使用。**
- **原因：**C ABI 比 C++ ABI 简单，但返回数据/错误字符串仍有分配方与释放方；用户 comparator/filter 回调及其销毁函数可能在库内被调用。
- **怎么测：**①用纯 C 消费者写、读、删除、批处理、迭代；②覆盖不存在 key、空 value、长错误消息；③按 API 用 `leveldb_free` 释放库返回的内存，不用调用方 `free/delete` 替代；④统计 comparator/filter 回调和 destructor 次数；⑤关闭所有句柄后检查泄漏；⑥用真实绑定再测一次并核对指针长度，区分空值与缺失。
- **预期：**成功和失败路径所有权明确、无双重释放/泄漏/跨堆释放，回调状态在关闭前有效。
- **怎么修：**在对应分配模块提供释放入口并让绑定调用；修正回调生命周期。不要拿下游违反已写明所有权规则的用法当成库必须兼容的契约。
- **验收：**匹配工具链下 C 和 C++ 消费者分别通过；C API 通过不自动认证 C++ DLL ABI。

### BC-06 安装目录、头文件、CMake 导出和迁移目录

- [ ] **目标/必要性：高，旧包不完整是已确认缺陷。**
- **原因：**打包路径处理可能把目录写成一个文件；从源码目录运行的测试可能偷偷用到源码头和 build 路径，掩盖安装包损坏。
- **怎么测：**①为每个包解压到新空目录；②枚举 15 个公共头，检查 `include/leveldb` 真的是目录，含 `db.h/c.h/export.h` 等文件；③只用解压包构建独立消费者；④隐藏原源码/build 路径，确认 include/link 不偷用它们；⑤把整个安装前缀移动到有空格的新路径重建；⑥检查 CMake package 文件、导入库/运行库齐全和依赖传播；⑦确认没把私有 GoogleTest 头作为交付接口。
- **预期：**新消费者无需源码树即可编译运行，移目录后仍可找到包；包内容与 BUILD-INFO 一致。
- **怎么修：**走 CMake install 后归档、解压后再测消费者，避免手工通配复制；按最终 ZIP/TAR 的目录表验收。
- **取舍：**必须修。旧已发布资产不能靠 main 新提交变正确；按实际发布策略标记弃用、撤换或发新版本，别静默改变已宣称不可变的哈希。

### BC-07 异常、RTTI、目录级 flag 与下游构建污染

- [ ] **目标/必要性：高，对 `add_subdirectory`/FetchContent 下游应兼容。**
- **原因：**上游全局改 flag、fork 默认改为跟编译器、以及 MSVC `_HAS_EXCEPTIONS` 的作用范围都可能造成不同 TU 看见不同 STL 定义，或消费者找不到 typeinfo。
- **怎么测：**①建立外层工程，库外另有使用异常/RTTI 的目标；②加入 LevelDB 前后比较其编译命令；③默认配置通过；④明确协调所有相关 TU 关闭 RTTI，再测选择关闭的模式；⑤MSVC 检查 `/EH*` 和 `_HAS_EXCEPTIONS` 是否一致；⑥检查 Debug/Release 各自结果；⑦单独记录 Kyoto Cabinet 等只在依赖存在时生成的目标。
- **预期：**LevelDB 不擅自改变无关下游目标；受支持的协调模式能链接；关闭异常不应变成“任意分配失败都可安全恢复”的承诺。
- **怎么修：**缩小 flag 作用范围，检查需要一致的宏，协调库与消费者构建；探测第三方能力时用正确 probe 环境。
- **取舍：**修污染值得；不值得为兼容历史坏默认而继续产生 ODR 或 typeinfo 缺失。

### BC-08 可选依赖探测与构建结果一致

- [ ] **目标/必要性：高，是“包能不能读我的数据”的前置条件。**
- **原因：**装了开发包也可能符号拼错、没链接、缓存了旧 `HAVE_*`；交叉编译 probe 可能没真正链接；宏大小写变化也可能影响手工构建。U 的普通 Zstd probe 有已知假阴性。
- **怎么测：**①全新 cache 下分别构建 codec 有/无的组合；②记录 `HAVE_SNAPPY/HAVE_ZSTD/HAVE_CRC32C/HAVE_TCMALLOC`；③检查真实链接依赖与生成的 port 配置；④让压缩/解压用例真的运行，禁止 skip 代替成功；⑤换 sysroot 做缺依赖负例；⑥搜索下游是否手写旧宏或覆盖 configure 结果；⑦CRC32C 关闭外部库后做相同数据 checksum 对照。
- **预期：**probe、链接、运行三者一致；主动关闭的能力可明确识别；CRC32C 内置实现仍生成兼容校验。
- **怎么修：**修符号/链接探测、独立构建目录、明确依赖及版本；下游手工配置要提供迁移说明，不能混用两份 port_config。
- **取舍：**必须修静默错误；不必永久保留错误宏当作公共 API，但必须调查实际下游是否依赖再决定过渡期。

### BC-09 默认窄字符路径兼容，是否由库直接做好

- [ ] **目标/必要性：高，若定位是上游替代品，建议默认兼容。**
- **原因/现状：**U 的窄 Win32 API 使用 native file-API code page；F0 固定 UTF-8；F1 已有 OFF 兼容模式但源构建仍默认 ON。旧下游没改参数就可能读错目录。
- **怎么测：**①在 ACP 936 系统用原调用程序生成 GBK 路径，不修改程序；②U 创建/写入/关闭；③保持调用程序原样，分别换 F1 默认、ACP 模式和候选默认 C；④测 ASCII 与中文路径；⑤再用 ACP 1252 或另一实际支持环境复测；⑥检查候选无额外 flag 时究竟生成什么模式，而不只看文档。
- **预期：**若采用兼容默认，旧应用无源码、无额外 CMake 选项也应访问同一个物理目录；UTF-8 模式另有清楚身份。
- **怎么修：**建议默认匹配 `AreFileApisANSI()` 对应的 ACP/OEM，库内转 UTF-16，所有操作统一使用宽 API。仅切 ON/OFF 默认值之前，先通过 BC-11/12 证明全链路一致。
- **副作用/决定：**保留上游代码页无法表示某些字符的限制；已用本 fork UTF-8 默认的应用要继续用 UTF-8 版本。选择默认值和包名要有发布说明，不能两边都声称完全不变。

### BC-10 不要通过自动猜编码掩盖兼容问题

- [ ] **目标/必要性：高，需要验证设计，而非强行实现“通吃”。**
- **原因：**某些字节序列对 UTF-8 和 GBK 都合法，却对应不同名字；先看能否 UTF-8 解码、或 not-found 后切换，都不能决定调用方原意。
- **怎么测：**①准备一组经过确认、在两种编码里都合法且解释不同的字节，保存两份宽字符解释；②分别只存在一个、两个都存在、两个都不存在；③测试 Open、CreateDir、Rename、Lock、Remove、GetChildren；④观察同一轮 DB 生命周期是否选了不同目录；⑤禁止拿真实库做删除试验。
- **预期：**选定模式后全生命周期只有一种解释；不能因路径存在与否或操作种类改变编码。不存在时不能悄悄创建“另一种解释”的新库。
- **怎么修：**明确默认与显式 UTF-8 变体，或将来设计每个 Env 固定的模式；不要增加随调用变化的全局猜测状态。
- **是否值得：**不值得承诺无标记字节同时支持两种解释。值得保证默认旧契约、提供明确新能力并说明取舍。

### BC-11 路径模式必须覆盖全部 Env 操作

- [ ] **目标/必要性：高，避免只修 CreateFile 却留下恢复/删除路径。**
- **怎么测：**①每种路径模式下依次测 CreateDir、NewWritableFile、AppendableFile、SequentialFile、RandomAccessFile、FileExists、GetFileSize、GetChildren、RenameFile、LockFile、UnlockFile、RemoveFile、RemoveDir；②文件名含中文、空格、共同前缀；③GetChildren 返回的字节必须能直接交回同一 Env，访问同一文件；④覆盖相对/绝对路径、正反斜杠、根目录/盘符根和尾部分隔符；⑤最后执行完整 DB 开、写、关、重开、compact 和只在副本上的 DestroyDB。
- **预期：**所有操作一致地解释路径，无遗漏文件、误删其他目录或恢复时转码两次。
- **怎么修：**集中使用同一转换策略，区分字节路径与宽路径的边界；修复根目录/UNC 的 dirname 处理时加入相应用例，不用字符串拼接猜根目录。
- **是否值得：**必须在支持的路径范围内兼容；长路径等额外范围交给 BC-13 明确评估。

### BC-12 日志、临时目录、环境变量的编码和失败可见性

- [ ] **目标/必要性：高，F1 已有修正，需要验收。**
- **原因：**DB 文件走宽 API、logger 走窄 CRT 会分裂；`TEST_TMPDIR`/系统临时目录可能在中文用户目录；logger 创建失败可能被静默忽略。
- **怎么测：**①分别把 DB、`TEST_TMPDIR`、系统临时目录放进非 ASCII 目录；②ACP/UTF-8 各测；③检查实际 LOG 在预期位置、能读到本次标记，不只看 Open 返回 OK；④让 logger 路径确实不可写，记录 Open 与诊断的现有约定；⑤在新进程中改变临时目录环境，避免缓存影响；⑥覆盖直接 NewLogger 与正常 DB 开库两条路径。
- **预期：**成功时文件路径与模式一致；失败时不写到另一目录。开库是否容忍诊断日志失败需明示，不能把“没有日志”误当“没有错误”。
- **怎么修：**统一 `_wfopen`、宽环境 API 和转换策略；错误信息应来自对应失败 API，不把不相关的陈旧 GetLastError 当根因。
- **取舍：**必须修编码不一致；是否把 logger 失败升级成开库失败是另一项行为政策，不宜未经评估直接变成致命。

## 5. 逐项清单：路径边界、读取与恢复

### BC-13 路径边界、长路径、无效字节与转换失败

- [ ] **目标/必要性：正常部署路径高；扩展能力按范围决定。** 本项是待覆盖边界，不是已经确认的新缺陷。
- **为什么：**ACP/UTF-8 转换、根目录提取、MAX_PATH、UNC 和 CRT 环境行为可能互相影响；非法 UTF-8 还可能被替换成别的字符。
- **怎么测：**①正常路径含空格、中文、非 BMP 字符；ACP 模式仅对可表示字符要求成功；②测试盘符根、相对路径、尾部分隔符、UNC；③若承诺长路径，测试超过传统 MAX_PATH 及匹配的系统/进程设置；④测试无效编码、嵌入 NUL、Windows 保留名等负例；⑤记录每种输入是否明确拒绝、被替换或截断，确认不会误碰另一真实数据库；⑥检查转换失败与过长结果的状态输出。
- **预期：**宣称支持的有效路径不丢失；不支持的输入有确定的错误或明确限制，不应误删/覆盖别的目录。不能把无效字节一律列为必须兼容的正常路径。
- **怎么修：**检查转换返回值和长度，明确非法编码策略，单独处理 Windows 根/UNC 规则；路径扩展支持需要整套 API 一致，不能只给一个 CreateFile 加前缀。
- **取舍：**本地常见合法路径值得兼容；任意无效字节、所有 Win32 保留语法不值得承诺。长路径和特殊命名空间依据下游实际需求决定。

### BC-14 `SequentialFile` 返回自有、复用、重叠缓冲区

- [ ] **目标/必要性：最高，已有历史漏读证据；F1 有修复。**
- **原因：**返回 Slice 不保证指向 scratch，下一次 Read 可能覆盖同一内部缓冲区。调用方必须在再次读取前保留有效字节。
- **怎么测：**①用真实 Writer 生成带校验的记录；②实现三种合法读取器：scratch、自有稳定缓冲区、每次复用的内部缓冲区；③分别足量读、每次 1/5/7 字节、不同分块长度；④覆盖小记录、跨 32 KiB block 的记录、多条连续记录和空 record；⑤添加合法重叠返回区域用例验证复制方式；⑥F0 作为坏对照，F1/C 复测；⑦每条比较字节与顺序，同时检查 corruption 回调计数。
- **预期：**F1/C 的所有合法实现返回完全相同的记录；不能将“0 corruption”或“读到 EOF”当成成功。
- **怎么修：**在下次 Read 前将实际返回内容保存到累积位置，重叠情况用 memmove；保留短读支持。不应要求已有合法 Env 改为只返回 scratch。
- **验收：**移除复制后至少自有/复用缓冲区用例失败，恢复后通过。底层实现返回超过 n 或悬空地址属于违约，应单独讨论防御，不能混入合法兼容承诺。

### BC-15 原生短读、EOF、零长度和错误后部分数据

- [ ] **目标/必要性：普通文件高；管道/设备支持不自动承诺。**
- **原因：**短读并不总等于永久 EOF；循环也必须对返回 0 终止，避免死循环；EINTR 和真实 I/O 错误应区分。
- **怎么测：**①对 SequentialFile 和 RandomAccessFile 分别测试足量、连续短读、零字节 EOF、Read(0)、偏移恰好到末尾/超过末尾；②用测试包装器注入中断、真实错误、已读部分后报错；③在返回数据量和状态上与契约对照；④平台真实普通文件路径复测；⑤如果下游用管道或自定义流，另测阻塞/结束约定，并设超时；⑥测试程序记录底层 Read 调用次数，防止忙循环。
- **预期：**普通文件不因暂时短读漏数据；0 返回会结束；真实错误不会伪装成功。错误同时带部分数据时按统一约定处理，不能留下未初始化 Slice 被上层误读。
- **怎么修：**正确累积、处理 EINTR/EOF、设置输出状态。只在设计确实支持流时新增流语义，不为假设中的设备场景破坏正常文件契约。
- **取舍：**保留短读修复；无证据的“所有特殊设备必须保持一次 read 即返回”不是默认阻止修复的理由。

### BC-16 真实 DB 的 WAL 恢复是否漏掉已确认写入

- [ ] **目标/必要性：最高，是 BC-14 的完整数据库验收。** 尚不能由过去组件证据代替。
- **准备：**待补独立恢复夹具/监督程序，使用真实 DB API 写入有效 WriteBatch；分别配置默认 Env 和返回复用自有缓冲区的 Env。
- **怎么测：**①Open 并同步写入确定性键值与批次；②外部监督程序记录已经收到的写入成功确认；③在合适阶段强杀写进程，保留 DB 副本；④用 U/F0/F1/C 各自恢复独立副本；⑤比较所有已确认键值、删除结果、迭代顺序、记录数；⑥恢复后再写新数据、关闭重开再次核对；⑦覆盖 `reuse_logs` 开/关和足量/短读。
- **预期：**已成功确认的 sync 写入在本实验支持的环境下不遗漏；尚未返回或监督程序未收到确认的那笔不能强行要求存在或不存在。
- **怎么修：**先定位 Reader、批次解析、恢复状态、文件清理哪个环节丢数据，修合法缓冲区契约，不靠默认忽略损坏或自动 Repair 掩盖。
- **验收/边界：**记录与完整 DB 内容吻合。`sync=false` 的物理断电持久性、进程死亡和机器掉电必须分开；本项不是物理断电认证。

### BC-17 不完整 WAL 尾部：第一次恢复后继续写，再次恢复

- [ ] **目标/必要性：最高，避免旧的尾部追加数据丢失。**
- **原因：**截断 record 后直接追加，下一次读取可能把新写入当成坏尾部的一部分；仅验证第一次 Open 不够。
- **怎么测：**①准备含多个有效批次的 WAL；②只在副本上构造短于 header、完整 header 缺 payload、碎片化 FIRST/MIDDLE 缺 LAST、block 边界尾部等截断；③记录哪些批次完整，哪些本来就不完整；④开库恢复并验证完整前缀；⑤写入新的同步批次并关闭；⑥再次打开核对旧完整前缀和新批次；⑦覆盖 `reuse_logs` 开/关及 Debug/Release。
- **预期：**不完整的未提交尾部可被忽略，但此前完整数据和恢复后新增数据不能因继续追加而消失。
- **怎么修：**识别不完整尾部并创建可安全写的新日志或采用经验证的截断策略；不能为了维持文件数/文件号与上游相同而恢复危险复用。
- **取舍：**必须保留正确恢复。文件编号、占用暂增、rename 次数变化属于次级观察，除非下游误把它们当协议，应修下游依赖而非撤销恢复修复。

### BC-18 不完整 MANIFEST 与重复开库

- [ ] **目标/必要性：最高，与 WAL 分开测试。**
- **原因：**MANIFEST 保存版本元数据，尾部损坏与 WAL 数据恢复不是同一条路径；状态误判可能导致 Open 失败或后续再开丢文件引用。
- **怎么测：**①从正常 DB 生成真实 MANIFEST 并保留所有依赖 SST；②在新副本截断最后一条 version edit 的 header/payload/fragment；③分别在存在可恢复完整前缀、缺少必需元数据两类夹具上开库；④可恢复者继续写、compact、关、重开两次；⑤记录 CURRENT、MANIFEST、文件清单和完整键值；⑥对确实不完整的必需信息检查清晰 Corruption，不自动造出“空的新库”。
- **预期：**能安全恢复的状态保持数据一致；不能证明有效的状态明确失败，不伪报成功。完整合法 MANIFEST 不受影响。
- **怎么修：**避免向不完整 MANIFEST 追加，正确设置 save/reuse 状态；不能仅靠改 CURRENT 指向任意存在文件让 Open 变绿。
- **取舍：**必须保护数据；不值得兼容历史错误成功。依赖更新前后文件号完全相同的测试要改为数据及引用正确性验收。

## 6. 逐项清单：文件系统、耐久性与数据库内容

### BC-19 MANIFEST 目录刷新权限和失败策略

- [ ] **目标/必要性：高，需要明确产品决定，不能只吞错误。**
- **历史事实：**普通 NTFS 临时目录可以打开并刷新；限定目录写属性权限后，创建/rename 子文件仍成功，而目录 GENERIC_WRITE 打开报 5。
- **怎么测：**①在专用临时目录保存原 ACL；②普通非管理员身份验证 file create/write/rename 与目录 sync；③仅在该目录建立受限 ACL，仍确认子操作成功；④触发真正的 MANIFEST 同步并记录 Open/Write 状态；⑤再注入目录 open 失败、目录 flush 失败、文件 flush 失败三类错误；⑥finally 恢复 ACL，核对无其他目录被改。
- **预期：**严格模式应传播实际失败；若将来设计降级，必须可选择、可观察，文档说明耐久性降低，不能只对所有 ACCESS_DENIED 无条件返回 OK。
- **修复选项：**A 明确只支持能够目录刷新的环境；B 显式兼容/降级模式加诊断；C 针对已证实不支持的文件系统设计替代机制并验证。默认选哪个要先决定 fork 的安全目标与下游范围。
- **取舍：**有真实受限部署时值得做兼容策略；不值得以虚假成功换“更容易开库”。ACL 模拟不是所有共享盘结论。

### BC-20 RenameFile 的覆盖、ACL、占用和错误语义

- [ ] **目标/必要性：高，保证正常 CURRENT 更新；差异先证实。**
- **原因：**MoveFileEx 与 ReplaceFile 的覆盖、安全描述符和失败行为可能不同。不能只从函数名推出网络盘一定回归。
- **怎么测：**①目标不存在、目标存在、同卷替换、源不存在、路径不存在；②源/目标权限不同，记录替换前后可访问性与 ACL；③另一个进程持有不同 share flags 的目标句柄，检查成功/失败和原目标是否保留；④只用受控句柄模拟占用，不关闭安全软件；⑤失败后重试并检查 source/target、CURRENT/目标 MANIFEST 一致；⑥若有下游按错误文本匹配，记录它真正依赖的类别。
- **预期：**失败不能破坏原有效库或把 CURRENT 更新到不存在文件；成功后独立句柄能见到完整新内容。跨卷不默认为支持范围。
- **怎么修：**针对已复现语义差异修权限/覆盖流程或限定支持；不要回到 delete-then-move 形成额外缺口。错误文本最好不作为稳定协议，保留正确 Status 类别。
- **取舍：**正常本地同卷覆盖必须兼容；保留某个旧 Win32 数字/翻译文本的必要性低，除非有实际下游证据。

### BC-21 文件系统和部署位置矩阵

- [ ] **目标/必要性：本地支持范围高；其余按真实需求决定。**
- **候选范围：**NTFS 为首轮；ReFS、exFAT/FAT、UNC/SMB、映射盘、重定向用户目录、同步盘占位文件、符号链接/junction 逐项标“支持/不支持/待测”，不要统称共享盘。
- **怎么测：**①记录每个位置的文件系统、服务端/客户端和权限；②重复正常开写关重开、锁、替换、目录 sync；③SMB 测网络中断前后和重连；④同步盘先让文件真实落地，另测未落地占位状态；⑤记录短名/大小写、网络延迟及真实错误；⑥每个位置做独立库，不在同一复制件上并发开写。
- **预期：**声明支持的格子保持一致；不支持者明确错误及说明。它们之间的正常复制兼容与断线时的安全保证分开。
- **怎么修：**有明确需求再针对文件系统实现，或将支持范围缩到本地可靠文件系统；不要用全局“忽略目录刷新失败”伪装全支持。
- **取舍：**无需穷尽所有 NAS 和云盘；必须如实列范围。仅测 NTFS 不得在发布说明宣称“Windows 任意目录均可用”。

### BC-22 物理耐久性、掉电及故障注入

- [ ] **目标/必要性：涉及“防止断电丢数据”的声明时最高。** 普通功能发布至少应准确限制承诺。
- **原因：**文件内容刷新、目录项更新、CURRENT 替换、旧文件删除顺序可能被存储栈重排；进程退出和内核掉电不是同一种故障。
- **怎么测：**①先列实际 durable-write 顺序与失败传播；②在测试 Env 中对各同步/rename/删除步骤注入失败；③另用可快照且隔离的虚拟磁盘/虚机试验意外断电，记录磁盘缓存与宿主设置；④以外部监督程序记录已确认 sync 写入；⑤检查掉电后实际保留的磁盘状态，先取得其恢复程序首次启动前的副本，再核对全部已确认数据；故障前快照只用于重置下一轮，不可拿它回滚后验证本轮耐久性；⑥重复多轮并保存失败样本；⑦最后才考虑专用硬件环境，不能在工作机上做断电试验。
- **预期：**不能把未确认写入当必须存在；不能丢已确认写入而宣称强保证。模拟通过只能覆盖它模拟的存储语义。
- **怎么修：**从确认失效的持久化顺序或 API 保证着手；若证据不足，缩窄“预防/完全防止”措辞，而不是把可见性测试重命名成耐久性测试。
- **取舍：**值得做严谨声明与注入；若不做物理实验，可明确“未验证物理掉电”，不阻止其他功能对照继续推进。

### BC-23 Snappy/Zstd 的实际块格式与升级/降级

- [ ] **目标/必要性：最高，对已有压缩库必须逐能力确认。**
- **原因：**压缩器可能因数据不够可压缩退回原样块；只写 Put、不关闭/生成 SST，或者从缓存读，都会把缺 decoder 的包测成假绿。
- **怎么测：**①准备高度重复且足以落盘的数据，分别 no-compression、Snappy、Zstd；②确保产生 SST；③检查实际 block trailer 类型，而不只看 Options；④结束进程，用新进程/新缓存读全量数据；⑤对每种写入方/读取方测试 U→C、F1→C、C→U、C→F1；⑥U 的 Zstd 探测缺陷须记录真实能力，不假装它有 decoder；⑦无 decoder 的负例记录对应读失败，不能只看 Open 是否 OK。
- **预期：**具备同 codec 能力者读回所有键值；缺 codec 的组合明确不支持，不能静默丢记录或自动清库。NoCompression 的正例始终单独存在。
- **怎么修：**为兼容包编入下游所需 decoder，或提供明确能力标识/不同包。切换 compression 选项通常只影响后来生成的块，不会立即把所有旧块转换；要降级必须先以具备 decoder 的工具完整导出/重建并验证。
- **取舍：**实际用户有压缩数据时值得提供匹配 decoder；不必声称任何无依赖小包都能读取全部 codec。不能只为了包小而让默认交付无法读目标下游旧库。

### BC-24 合法数据库内容和正常读写语义

- [ ] **目标/必要性：最高，是兼容性主验收。**
- **怎么测：**①用第 3 节确定性数据分别由 U/F1/C 创建正常关闭的 DB；②每份库复制后交给其他版本读取，统计全量 key/value 与迭代顺序；③逐项覆盖覆盖写、Delete、WriteBatch 原子性、snapshot、迭代起点/终点、空 key/value 和内嵌 NUL；④做 reopen、显式 compact 和再次读取；⑤比较 sync/非 sync 正常关闭两类；⑥确认跨版本所需 codec、比较器一致。
- **原因：**编译/开库通过可能掩盖 value 截断、迭代漏项或恢复状态不同；二进制 key/value 不应走路径编码转换。
- **预期：**合法数据语义一致；读写目录名改变不要求转换 key/value。实现内部文件布局、层级和文件号不要求逐字节相同。
- **怎么修：**定位真实数据路径，修合法数据差异；先排 codec、比较器、误开另一目录与不一致备份。
- **取舍：**必须兼容合法数据，不能用“现在更严格”解释正常数据库被误拒绝。

### BC-25 自定义比较器、FilterPolicy、缓存和自定义 Env

- [ ] **目标/必要性：高，这些是公开扩展点；内部私有行为另算。**
- **原因：**公共头不变不代表调用时机、对象生命周期、Name 或返回内存约定都不变。
- **怎么测：**①使用寿命覆盖 DB 的自定义 Comparator/FilterPolicy/Cache/Env；②记录比较器名并用同一实现跨版本开库；③用 Bytewise 与一个确定性的自定义排序作正例；④换比较器名作应失败负例；⑤检查 Bloom/filter 有无时键值一致；⑥缓存开/关、空值/大值和边界 key 复测；⑦配合 BC-14 自有缓冲区与资源限额测试。
- **预期：**合法扩展点保持契约；更换排序规则却沿用同名不应被当成合法兼容输入。Cache 关闭可以变慢，但不能变结果。
- **怎么修：**恢复公开返回值与生命周期约定；如果需要新扩展，避免要求所有现有 Env 强制实现额外纯虚函数。
- **取舍：**公开扩展点值得兼容；Chromium/Minecraft 私有磁盘格式和内部头不是自动承诺，需要单独列产品范围。

### BC-26 损坏数据防御检查是否误拒绝合法数据

- [ ] **目标/必要性：合法数据高；保留历史越界行为为零。**
- **原因：**block 长度加法溢出、越界 handle、过短 internal key 曾可能触发越界；新检查应拒绝坏输入，同时不能把合法边界判错。
- **怎么测：**①先用 BC-24 的所有合法库作为正例；②在独立副本构造尺寸边界、溢出长度、超出文件的 handle、短 internal key；③分别 Debug/Release 和可用内存检查工具运行；④对比 Status/日志/崩溃，区分已有 assert 与 Release 越界风险；⑤确认文件没有在失败读取时被擅自重建；⑥实际执行现有 `RejectsOverflowingEntryLengths`、`OversizedBlockHandle` 等用例并记录命中数。
- **预期：**合法边界通过；坏输入安全拒绝或符合已定义调试断言，不能靠返回一个巨大的 Slice 去读内存。不能把几条测试推广成“任意损坏绝不会崩溃”。
- **怎么修：**只修误判或缺失的边界检查；若下游依赖读取“轻微损坏”库，提供显式离线救援流程，不放松正常读路径的内存安全。
- **取舍：**不兼容坏输入的历史错误成功通常应接受；改变错误类别或 Debug assert 时可单独改善，但不能撤销安全修复。

### BC-27 `RepairDB` 的损失范围、返回值与误用

- [ ] **目标/必要性：中高，必须如实说明，不能承诺无损。**
- **既有契约：**上游本来就是尽力恢复并可能丢数据；ScanTable 已跳过无法解析的 key。把新 RepairTable 过滤描述成破坏“全有或全无”保证是不正确的。
- **怎么测：**①正常库 Repair、损坏 SST、坏 WAL、缺失表等分别独立复制；②Repair 前保存预期完整键值和可恢复子集；③记录归档文件、丢弃条目、返回 Status；④成功后正常 Open、遍历、写新值、关闭重开；⑤确认坏 key 不流入新表；⑥再对 U 做同样对照，分别记录恢复更多、恢复更少、报错和崩溃。
- **预期：**无损夹具不丢合法数据；损坏夹具尽量保留可证实的有效条目，任何损失明确记录，不把 Repair OK 解释为全数据恢复。
- **怎么修：**修误删有效条目、重建元数据/归档问题和崩溃；保留必要过滤。正常 Open 不应因为这项测试被改成静默自动 Repair。
- **取舍：**有效数据回收值得优化；不必保留无法解析的非法 key。救援行为与默认兼容性要分别发布说明。

## 7. 逐项清单：可见行为、平台与实际下游

### BC-28 CURRENT 的 LF、CRLF、CR 和非法内容

- [ ] **目标/必要性：中，保留兼容 Windows 文本换行的能力。**
- **原因：**结尾 CR 若残留在 MANIFEST 文件名里会找不到文件；但宽松接受外部改写不等于可以接受任意错误元数据。
- **怎么测：**①由正常库复制出 LF、CRLF、单 CR、无终止符、空文件五组；②明确 MANIFEST 实际存在；③分别开库并检查键值；④对拒绝组恢复原 CURRENT 后再次开库，证明失败没有破坏数据库；⑤增加额外空白、重复终止符、错误文件名、指向不存在 MANIFEST 负例，记录实际处理而不提前假定都必须接受；⑥用实际 `CurrentFileTerminator.*` 参数化用例校准。
- **预期：**约定支持的三种终止符访问同一 MANIFEST；缺终止符/空文件应拒绝；错误指针不能变成创建空库成功。
- **怎么修：**严格按选定规则剥除末尾终止符，保持正常写出格式；针对额外输入确定拒绝或容忍政策，不能只靠不断 trim 让所有内容通过。
- **取舍：**兼容 CRLF 值得，单 CR 是有意扩展；不必为了模仿上游拒绝 CRLF 而撤销修复。不要把接受 CR 自动描述成合法库格式变化。

### BC-29 LOG 追加、轮换、诊断保留与磁盘占用

- [ ] **目标/必要性：中，属于可见运维行为。**
- **原因：**直接 NewLogger 重开和正常 DB 开库不是同一条路径；后者仍尝试 LOG→LOG.old。轮换失败、占用或路径错误会改变结果。
- **怎么测：**①直接 NewLogger 写标记 A、关闭重开写 B；②正常开/关 DB 多轮，每次写可识别标记；③记录 LOG/LOG.old 大小与内容；④用受控只读/占用条件让轮换失败；⑤检查是否仍写入预期目录、是否截断旧诊断；⑥确认采集脚本只要求自己的明示格式，不误把追加模式当无限历史留存。
- **预期：**直接重开保留 A/B；正常轮换按现有设计执行；诊断失败不伪装数据写成功或写到别处。
- **怎么修：**编码/错误处理按 BC-12；若需要日志限额/轮换策略，单独设计，不回退到每次 NewLogger 截断历史。
- **取舍：**不必兼容“重开即删除旧诊断”的历史行为；有真实磁盘占用问题再提供保留策略，并说明不属于数据格式兼容。

### BC-30 NowMicros 的精度、单位、回退和非单调性

- [ ] **目标/必要性：低至中，先确认实际下游是否依赖。**
- **原因：**更精确的系统墙钟会改变数值步进；它仍可能因系统时间调整倒退，不适合被偷偷当单调计时器。
- **怎么测：**①记录连续调用分布、单位与基准；②普通环境验证精确 API 路径；③通过隔离测试封装验证缺少该入口的回退，不在工作机修改系统时间；④检查下游 TTL、耗时、超时和排序是否错误依赖严格递增；⑤将只接受精确固定时间差的测试改成验证实际契约。
- **预期：**单位/既有时间基准不意外改变，回退可用；不要验收“永不倒退”这项未承诺行为。
- **怎么修：**保持 NowMicros 契约；需要耗时测量的下游采用真正的单调时钟，若库新增单调接口则单独设计兼容扩展。
- **取舍：**一般不值得维持旧粗精度；若有真实应用把数值写进持久数据或协议，先确认它依赖的基准与单位再决定迁移。

### BC-31 错误类别、输出参数、错误文本和诊断

- [ ] **目标/必要性：高在数据安全/类别；低在逐字文本一致。**
- **原因：**API 切换后错误码/消息语言可能不同；CRT 失败与 Win32 GetLastError 来源不同；旧输出指针可能让下游误用失败对象。
- **怎么测：**①不存在路径、权限拒绝、文件被占用、磁盘满/配额、坏数据分别注入；②检查 Status 的 OK/NotFound/IOError/Corruption 及输出对象；③成功后再故意失败，确认没有复用旧指针或旧值；④检查实际下游是否解析错误文本；⑤观察恢复代码是否忽略/降级真实错误。
- **预期：**失败不返回可被当成功的新对象，不静默清库；正常 Get 的 key 缺失与文件系统 I/O 故障不混淆。逐字消息或翻译版本不是默认承诺。
- **怎么修：**按失败 API 取对应错误，正确初始化输出参数；下游改为检查稳定类别。若旧错误类别本身错误，修正时明确写迁移说明。
- **取舍：**保证有用类别和不虚报成功很值得；为保持某个本地化句子或偶然 Win32 数字而倒退实现通常不值得。

### BC-32 资源限制、mmap、零长度文件和短写

- [ ] **目标/必要性：中高，先区分新增回归与基线已有问题。**
- **原因：**不同读取路径、资源耗尽、句柄生命周期或单次系统写不足会暴露问题；这些并非自动由本次 diff 引入。
- **怎么测：**①普通与强制非 mmap 读取；②零长度文件、文件边界、重复打开关闭；③在隔离进程控制句柄/映射限额，触发失败后恢复；④用测试 Env 注入短写、close/flush 错误；⑤检查文件实际长度、状态、句柄/内存增长；⑥若承诺大文件 Env 能力，用稀疏文件测大偏移，不能把 SST 默认大小选项误当全接口硬上限；⑦U/F1/C 同测。
- **预期：**受支持路径数据一致；资源失败清楚返回、释放已分配资源；未完成写入不能错误返回成功。
- **怎么修：**只根据复现修读写循环、计数和 RAII 释放；U 已有同病要在报告标为历史缺陷，可另修，不伪称 fork 新回归。
- **取舍：**一般资源和写入正确性值得；无限资源耗尽、任意恶意 Env 内存行为不属于可保证范围。

### BC-33 文件锁、重复打开和多进程边界

- [ ] **目标/必要性：高，必须避免把错误目录当成锁成功。**
- **原因：**转码错误可能打开另一份 LOCK；网络文件锁、同一路径别名和多进程竞争又有各自范围。LevelDB 不承诺多个独立进程同时写同一个 DB。
- **怎么测：**①两个进程用同模式、同物理目录依次尝试 Open；②同进程重复 Open；③首进程正常关闭/被杀后重开；④用大小写、相对/绝对路径或受支持的目录别名访问同物理位置；⑤混用 ACP/UTF-8 时明确传入各自正确字节，检查物理路径一致；⑥共享盘锁另按 BC-21 记录。
- **预期：**不允许的第二写入者得到明确失败；释放后可用。不能靠删除 LOCK、忽略锁失败或偷偷创建另一目录绕过。
- **怎么修：**修路径身份或锁实现的真实缺陷，限定支持文件系统；多写者需求应改架构，而非兼容补丁中强行开放。
- **取舍：**正常互斥必须保持；“兼容多个同时写者且保证无损”不是本 fork 直接替换的合理目标。

### BC-34 OS、架构、工具链最低版本和系统依赖

- [ ] **目标/必要性：对宣称支持的平台高；其他按需求决定。**
- **原因：**精确时钟动态回退并不代表所有 CRT/编译器产物都支持旧 Windows；x64 在 ARM64 仿真运行也不等同原生 ABI；Linux libc 基线影响旧机加载。
- **怎么测：**①写清最低 Windows/Linux/libc/编译器/C++ 标准；②在最老支持系统用最终包运行消费者；③检查 DLL import 或 shared-object 动态依赖；④实际要发 ARM64/x86 时分别构建运行，仿真与原生分别记录；⑤系统 ACP 为 65001 时把旧编码差异校准标为不适用，不伪报已覆盖非 UTF-8 ACP。
- **预期：**支持组合可加载并完成完整消费者操作；未支持组合在发布选择上清晰可辨。
- **怎么修：**匹配工具链/运行库或提升最低系统并说明；必要时提供不同构建，而非仅靠函数 GetProcAddress 回退宣传全平台兼容。
- **取舍：**不必为没有实际用户的所有旧平台付出维护成本；要先决策，再提供明确的有限支持表。

### BC-35 编译警告、下游 `/WX` 与 CI 的假绿

- [ ] **目标/必要性：中在警告兼容；高在验证可信度。**
- **原因：**新增私有 warning flags 可能在某个编译器被当无效参数；另一方面测试不命中、依赖 skip 或只编译没有运行也会“绿”。
- **怎么测：**①用实际下游 `/WX` 或 `-Werror` 构建 U/C；②查看库与消费者各自命令，确认 flag 作用范围；③列出测试再按实际名字执行；④XML 校验数量、失败和 skipped；⑤保留依赖缺失、删掉缓冲区复制等应失败负例；⑥运行会临时修改源码的校准器前后核对工作树一致；⑦超时/异常中断后的恢复也要检查。
- **预期：**受支持编译器无错误 flag；CI 不把 0 tests 或 skip 当覆盖。两者均失败时先记录共同环境原因。
- **怎么修：**按工具链条件化 warning，修真正诊断；补计数/skip/超时与产物记录，不用空断言填测试数。
- **取舍：**有真实 `/WX` 下游时值得兼容；不能无限承诺未来所有编译器的新 warning 都零告警。没有实际复现不能把“可能 /WX 红”列为确认回归。

### BC-36 逐个验证最终包，而非仅验证打包脚本

- [ ] **目标/必要性：最高，是交付门槛。**
- **现状：**当前 release 有 22 个定义变体；`tools/release/check.py` 的静态检查不执行这些平台构建，也不证明线上资产正确。
- **怎么测：**①枚举本次真正准备发的每个资产，标平台/架构/配置/静态-DLL/路径模式；②逐包哈希、目录表、头文件和 BUILD-INFO；③从解压前缀构建运行独立消费者；④Windows 明确查实际 LOG、路径模式和 CRT；⑤依赖在干净环境重新检查；⑥CMake consumer 未注册 CTest 的情况要直接运行实际可执行文件，不能把 `ctest` 的 0 tests 算通过；⑦对不能在本机运行的目标用对应环境或标未验证。
- **预期：**每一个“已验证”资产都有独立运行证据；不能把某个 DLL 包成功外推到其他 21 格。
- **怎么修：**对失败变体修安装/元数据/运行库/依赖并重新生成新身份包；若没有能力验证，可以缩减发行范围，不能造绿。
- **取舍：**必须覆盖准备宣称可用的包。暂时不发部分矩阵是合理取舍，胜过发一批无法复现或不完整的包。

### BC-37 真实下游：源码替换、库替换和用户数据

- [ ] **目标/必要性：最高，至少选一个真实目标下游。**
- **准备：**例如 librime 的一个固定提交和它当前使用的 LevelDB 版本；仅用一次性测试用户目录与经授权的数据副本，不接管正在使用的输入法用户目录。
- **怎么测：**①先原版依赖构建/运行，记录环境；②仅替换 LevelDB，其他依赖和配置不变；③分别测源码集成、静态重新链接、DLL 二进制替换，不混称；④正常库、非 ASCII 用户目录、已有 Snappy 库、自定义 Env/缓存若有就覆盖；⑤做正常输入/更新/退出/重启；⑥验证全部测试词条或数据，不只测程序启动；⑦观察锁、日志、升级和回退。
- **预期：**不需要旧源码调用方改路径编码，或若未决定兼容默认则明确记录仍需模式选择；合法数据不减少，不触发额外自动重建/Repair。
- **怎么修：**归因到前面对应 BC 项，避免只针对某个程序打特殊补丁让演示通过；若下游使用私有扩展，单列适配范围。
- **取舍：**值得优先服务实际下游；不应由一个下游通过宣传对所有应用/私有 fork 通用。

### BC-38 延迟、磁盘占用和耐久性成本

- [ ] **目标/必要性：中，部署前评估，但不能以回退正确性换分数。**
- **原因：**目录 sync、WRITE_THROUGH、不能复用不完整日志、codec 启用都会改变耗时或文件数量。
- **怎么测：**①U/F1/C 同机同盘同数据，分正常/恢复、sync/non-sync、codec 开/关；②多轮记录 Open、批次写、Sync、Compact、reopen 的分布，不只单次耗时；③记录 I/O、文件数和空间；④共享盘单独测；⑤提前写可接受阈值与目标场景，避免看到结果才临时改验收；⑥将性能分布与正确性结果并列保存。
- **预期：**识别可量化成本和是否满足实际下游要求；更慢本身不自动等于契约破坏。
- **怎么修：**减少多余系统调用、改善批处理/配置和文档；任何耐久性降级要显式选择并说明，不能默默取消 flush。
- **取舍：**高成本确实阻碍使用时值得优化；文件编号变化或少量恢复文件增加通常不值得撤销数据安全修复。

### BC-39 升级后的回滚、旧包弃用与数据迁移

- [ ] **目标/必要性：高，升级计划必须包括退回去。**
- **原因：**新库写出旧构建没有 decoder 的压缩块、路径模式变化、元数据恢复或旧包头文件缺失，都会让“把 DLL 换回去”不等于可回滚。
- **怎么测：**①保留干净关闭的升级前备份与库外数据摘要；②候选写入新数据、compact、关闭；③复制升级后数据交给拟回退的旧版本，确认 codec/比较器匹配；④读取全部数据并执行受控写/重开；⑤不能读的组合记录明确原因；⑥演练从备份或逻辑导出恢复，验证恢复点，不覆盖唯一原件。
- **预期：**回滚边界明示；可以回滚的组合完整读写，不可回滚者提前知道需要 decoder、导出/重建或停写。
- **怎么修：**交付匹配 decoder/路径版本，提供经验证的迁移步骤；发布说明标明旧损坏资产及替代版本，不靠重名覆盖让用户猜。
- **取舍：**应提供面向目标下游的可执行回退；不必保证任何缺能力的老版本都读后来显式启用的 codec。

### BC-40 发布决策：兼容范围、未解决项和保留警告

- [ ] **目标/必要性：最高，最后做，不先写“兼容完成”。**
- **怎么做：**①为每个 BC 项签署处理决定和证据路径；②高必要性正常输入/数据项必须通过，或明确不属于发行承诺；③依赖、路径、CRT、平台范围写入 README/兼容文档/包元数据；④列不能直接替换的组合与已知未测项；⑤每个声明兼容的实际资产有 BC-36 证据；⑥真实下游与回滚完成；⑦最后才决定是否调整 README 开头警告。
- **预期：**发布说明描述“在哪些组合验证了什么”，而不是“头文件没变，所以完全兼容”。失败、skip、未测、明确不支持分别标记。
- **怎么修：**未达标时继续保留警告；修证据对应的代码/包/文档，必要时缩减发行范围。
- **不做的事：**本清单不会自动决定发版、更新资产、推送或移除警告。那是后续单独操作。
- **取舍：**保留有限、真实的兼容范围比承诺任意下游通用更有价值。无需把每个历史坏行为做成一个开关。

## 7A. 逐项清单：2026-11-07 加固波的新增检查面（基线 W，BC-41～BC-48）

2026-11-08 拉取远端确认 `f11fe16..dc2fe63` 合入 29 个提交（远端 main 曾经历一次非快进更新，本地分支基线仍连续）。方向与既有原则一致：有效数据不变、坏输入更早明确报错、错误不再虚报成功。每条要验证的正是三个边界——**有效数据不变、新错误路径对下游可见、以前能打开的坏库现在明确拒绝**。这些检查是补充 BC-23～27、BC-07/15/32 的，不推翻它们。

### BC-41 解压缩预校验、noexcept 分配与 Zstd 哨兵（#1354 回移 + [edba255](https://github.com/takomitkm/leveldb/commit/edba255) + nothrow 分配）

- [ ] **目标/必要性：高（有压缩数据的下游）。**
- **W 的新行为：**声明解压长度 > 8 MiB（`kDecompressionFastPathBytes`）的块先经有界流式校验再分配（`table/format.cc`）；原始块/解压缓冲分配失败返回 `Corruption` 而不是抛 `bad_alloc`——本 fork 默认开异常，以前 `catch (bad_alloc)` 的下游现在收到的是 Status；`Zstd_GetUncompressedLength` 拒绝 `ZSTD_CONTENTSIZE_ERROR/UNKNOWN` 及超过 `size_t` 的哨兵（以前 UNKNOWN 会当成巨大长度去分配）。
- **怎么测：**①BC-23 的真实压缩正例逐 codec 重跑（普通块走一次性快路径，逐字节读回一致）；②阈值两侧（≤8 MiB / >8 MiB）的合法大块都能解码且结果一致；③zstd：声明窗口 ≥2^28 而载荷正常（一次性解码接受）的帧必须被接受（edba255 把 `ZSTD_d_windowLogMax` 提到 30）；尾随零载荷 skippable 帧、一帧结束后输入有剩余的多帧序列，累计输出必须等于声明长度；④**无内容长度头的外来 zstd 帧**（流式写出）现在拒绝——一次性解码本来也服务不了它，记录为一致性限制；⑤注入分配失败（限额 Env/低内存进程），断言 Status 且无异常逃逸；⑥**zstd 用例只在 optional-deps 任务真跑**（常规单元无 zstd 会 skip），本机/校机验证必须带 zstd，不许 skip 算通过。
- **预期：**合法数据零变化；坏声明在分配前被拒；失败经 Status 可见。
- **取舍：**必须验证；不恢复无界分配。哨兵拒绝属于新增严格性，写进文档即可。

### BC-42 `TableBuilder::ChangeOptions` 公共契约收紧（#1340 回移 + [9789dab](https://github.com/takomitkm/leveldb/commit/9789dab)）

- [ ] **目标/必要性：高（直接使用公共 `TableBuilder` 的下游）；对普通 DB 无影响——已核对 fork/main 非 test 代码中无内部调用方。**
- **W 的新行为：**中途换 `filter_policy`（以前静默接受，`Finish()` 空解引用）、`block_restart_interval < 1`、`Finish()`/`Abandon()` 之后调用——现在一律 `InvalidArgument`；切换前先 flush 待写数据块，flush 的 I/O 错误**从本调用立即返回**（以前存进粘性状态却返回 OK、选项照换），任何失败选项保持不变。公共头 `include/leveldb/table_builder.h` 仅注释变化（BC-02 口径不变）。
- **怎么测：**①合法中途切换（只改压缩等允许项）在 F1 与 W 用同一数据流各建一次表、逐字节比对：**待写块现在按旧设置封口，重启点布局可能与旧构建不同**——若不同，记录为可见布局变化并验证两种表都能读回；②每种新拒绝路径断言 `InvalidArgument` 且选项未变；③flush 失败注入：断言错误立即返回，后续 `Add`/`Finish` 得到粘性错误；④grep 确认目标下游是否真在用 `ChangeOptions`——没有的话本项降级为 API 回归测试。
- **预期：**合法用法读回一致；无效用法从崩溃/静默坏表变成明确错误。
- **取舍：**保留收紧；"兼容旧的崩溃行为"不在目标内。

### BC-43 compaction 与 `BuildTable` 对非法内部键改为失败（#1335 回移 + [bf7212e](https://github.com/takomitkm/leveldb/commit/bf7212e)）

- [ ] **目标/必要性：高（损坏库处置政策变化）。**
- **W 的新行为：**输入流中出现解析不了的内部键，compaction 现在返回 `Corruption` 且输入文件保持被 MANIFEST 引用（以前跳过坏记录仍可能"成功"，悄悄销毁记录和证据）；`BuildTable` 先验证首键再建文件（不留半成品），内部拒绝统一走 `Abandon()`+清理；`GetInternalKey` 委托 `DecodeFrom` 让规则集中。
- **怎么测：**①损坏 SST 参与手动 compaction：W 返回 `Corruption`、文件仍被引用、数据未删；F1 对照旧行为；②首键非法时不产生新表文件；③WAL 恢复路径确认坏批次仍按 BC-17 跳过——compaction 的失败只针对进入表构建阶段的非法键，两类口径分开记录；④损坏库走 RepairDB（BC-27/BC-44）的恢复对照。
- **预期：**不再静默丢记录；错误明确、库保持可 Repair 状态。
- **取舍：**值得。以前"能 compact 掉坏数据"不是要兼容的行为；依赖它的下游按 BC-31 改错误处理。

### BC-44 repair 输出变化：空表归档与元数据重算（[01b0196](https://github.com/takomitkm/leveldb/commit/01b0196) + [0959c2f](https://github.com/takomitkm/leveldb/commit/0959c2f) + [4b6a977](https://github.com/takomitkm/leveldb/commit/4b6a977)）

- [ ] **目标/必要性：中高（修 repair 正确性，输出与旧构建不同）。**
- **W 的新行为：**`ScanTable` 零有效条目的表归档且**不进新 MANIFEST**（以前会把空边界的表元数据推进版本）；归档按盘上实际文件名（旧表是 `.sst`，以前归档不存在的 `.ldb` 名会留原文件在原地、被下次 `Open()` 删掉丢证据）；`RepairTable` 从实际保留的记录重算 smallest/largest/max_sequence（以前可能发布空边界 → debug 断言 / release 写坏 MANIFEST，`LastSequence=0` 导致后续写入复用序号被 repaired 记录压制）。
- **怎么测：**①含"结构有效但零条目"表的库 repair：新 MANIFEST 不引用它、原文件在归档处、文件名与盘上实际一致、证据未被删；②瞬态 I/O 失败转入 `RepairTable` 的夹具：重建表边界/序号来自实际记录，repair 后继续写入不产生序号回退（对照旧构建的坏结果）；③据此更新 BC-27 的期望值：修复产出现在"更少引用 + 更准边界"，损失范围仍非全有或全无。
- **预期：**repair 产物可开库、边界正确；证据保留。
- **取舍：**保留。文件数/归档名变化按 BC-39 升级说明记录。

### BC-45 varint 与 MANIFEST 解码严格性、合法编码兼容（[7d10a9a](https://github.com/takomitkm/leveldb/commit/7d10a9a) + [07e88e8](https://github.com/takomitkm/leveldb/commit/07e88e8) + version_set 哨兵 + dbformat 防御）

- [ ] **目标/必要性：中高（坏库行为矩阵扩充）。**
- **W 的新行为：**varint 第 5/第 10 字节溢出解码类型 → 解码失败（返回 nullptr，输入输出都不动）；**冗余续字节编码仍接受**（07e88e8 钉住）；MANIFEST `next_file_number == UINT64_MAX` → `Corruption`（以前 `next+1` 回绕到 0，与活文件号冲突）；MANIFEST edit 解码期拒绝非法内部键；短内部键在 `InternalKeyComparator` 里按长度排序，不再越界。
- **怎么测：**①`Coding.Varint*` 实跑：合法值全过、溢出拒绝、失败不改输出、冗余编码仍收；②BC-24 正例库确认无 varint 误伤；③构造 `next_file=UINT64_MAX` 的 MANIFEST：明确 `Corruption`，不再文件号回绕；④把"以前能开、现在 Corruption"的坏库类型并入 BC-26 的负例矩阵，逐类确认拒绝路径不删除文件。
- **预期：**合法数据零变化；坏输入确定拒绝且证据保留。
- **取舍：**保留；不提供"按旧方式容忍溢出"的开关。

### BC-46 Windows ≥4 GiB 单次读分块（[0a472d3](https://github.com/takomitkm/leveldb/commit/0a472d3)）

- [ ] **目标/必要性：中高（外来大块库在 Windows 上的读取正确性）。**
- **W 的新行为：**非 mmap 随机读的单次请求 ≥2^32 时，旧代码把长度直接放进 `ReadFile` 的 `DWORD`——2^32 截断为 0、对实际存在的数据报空读（`ReadBlock` 按 handle 决定请求长度，外来大块可触发）；现在按 DWORD 上限分块，短读语义与旧实现一致，**<4 GiB 仍是一次 `ReadFile`**；mmap 路径不受影响。
- **怎么测：**①`env_windows_test HugeReadRequestServedInChunks`（win-quick）：测试按契约提交 4 GiB scratch，内存不足时按设计优雅 skip——**记录为 SKIP，不算通过**；②边界：恰好 2^32−1、2^32、2^32+1 的请求；③与 BC-15 的短读包装器叠加，验证累积语义与 EOF 处理；④常规库（块 ≤4 MiB）确认仍走单次调用路径。
- **预期：**大请求读到真实数据；普通路径行为不变。
- **取舍：**保留。这不是"DB value 支持 4 GiB"的承诺——公共 value 上限仍受 `write_buffer_size`/`max_file_size` 约束。

### BC-47 MSVC `_HAS_EXCEPTIONS=0` 目录级定义与 ODR（[95c4be4](https://github.com/takomitkm/leveldb/commit/95c4be4)）

- [ ] **目标/必要性：高（BC-07 的 MSVC 例外关闭矩阵按新实现重验）。**
- **W 的新行为：**`LEVELDB_DISABLE_EXCEPTIONS=ON` 且 MSVC 时，`_HAS_EXCEPTIONS=0` 从 leveldb target 私有改为**目录级**（`add_compile_definitions`）——本目录内所有 TU 的 STL 一致，消除同一内联函数两份定义的 ODR；目录属性不向上传播，`add_subdirectory()` 消费者不受影响（CMake 语义，需实测确认）。
- **怎么测：**①exceptions-off 的 MSVC 全构建（库+tests+benchmarks）编译并跑测试；②ODR 观察点：tests 与库同链时不再出现"链接器任选一份"的混定义（若有旧构建的复现记录，对照消失）；③`add_subdirectory` 外层工程：消费者目标编译命令**不含** `_HAS_EXCEPTIONS=0`；④Kyoto Cabinet 基准在 exceptions-off 下的结果单独记录——`/EHs-c-` 仍只作用于 leveldb target，宏却是目录级，这个组合的实际编译结果写进证据。
- **预期：**ODR 消除、消费者不受污染；③④有异常按证据修。
- **取舍：**保留。这是对 aa0c122 目标级方案在 MSVC 上的修正，不是兼容性回退。

### BC-48 新增测试护栏纳入验收（[07e88e8](https://github.com/takomitkm/leveldb/commit/07e88e8) + [8c226e0](https://github.com/takomitkm/leveldb/commit/8c226e0) + [238ac77](https://github.com/takomitkm/leveldb/commit/238ac77)/[b8ef93f](https://github.com/takomitkm/leveldb/commit/b8ef93f)）

- [ ] **目标/必要性：高（防"全绿但带伤"重演——这波回移就是继承了全套件绿、随后后验审查抓出多个缺陷的例子）。**
- **新增护栏：**`BuilderTest.*`（新套件，已注册 CMake）、`CorruptionTest.CompactionFailsOnInvalidInternalKey`、`TableTest.ChangeOptions*`、`ReadBlockIssue1349Test`（optional-deps 断言 zstd 用例真跑、禁止 skip、套件不得少于既有数量，b8ef93f 后 read-block 共 14 个）、`BlockTest.RestartOffsetMustBeUint32Representable`（真实 4 GiB 块，内存不足优雅 skip）、`RecoveryTest.ManifestNextFileNumberOverflow`、`Coding.Varint*`、`RepairTableRecomputesMetadataAfterTransientError`、`HugeReadRequestServedInChunks`。
- **怎么测：**①在带 snappy/zstd 的环境实跑 optional-deps 与上述套件，记录 XML 数量/skip（衔接 BC-35/BC-36）；②两个 4 GiB 相关用例在内存允许的机器跑真块，不允许的机器标注 SKIP 而非通过；③变异抽检：任选 2 个新护栏回退对应修复确认变红（不必对全部 48 项做变异）。
- **预期：**护栏真实执行、数量与 CI 断言一致；绿不被 skip 稀释。
- **取舍：**这是执行纪律，不是新增兼容承诺。

### 9.2 未来的基础构建/定向检查命令

以下是**以后放在校机 runner 中执行的 PowerShell 脚本模板**，本次没有执行。先准备匹配工具链和仓库要求的测试依赖；不要在本机安装环境。路径通过参数传入，ACP/UTF-8 和静态/DLL 使用不同 Source/Build。示例先演示 Release、静态库、ACP；不要把这一个配置的结果外推到 DLL 或其他包。

```powershell
param(
    [Parameter(Mandatory=$true)][string]$Source,
    [Parameter(Mandatory=$true)][string]$Build,
    [Parameter(Mandatory=$true)][string]$Prefix
)
$ErrorActionPreference = 'Stop'
# 使用已准备好的校机工具链环境；从独立 runner 目录启动。
cmake -S $Source -B $Build -DBUILD_SHARED_LIBS=OFF `
    -DLEVELDB_BUILD_TESTS=ON -DLEVELDB_BUILD_BENCHMARKS=OFF `
    -DLEVELDB_WINDOWS_UTF8_PATHS=OFF `
    -DHAVE_SNAPPY=OFF -DHAVE_ZSTD=OFF -DHAVE_CRC32C=OFF -DHAVE_TCMALLOC=OFF `
    -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=$Prefix
if ($LASTEXITCODE -ne 0) { throw 'configure failed' }
cmake --build $Build --config Release --parallel 2
if ($LASTEXITCODE -ne 0) { throw 'build failed' }
# 先列出测试，再执行；需要人工/后续脚本核对确实命中。
ctest --test-dir $Build -C Release -N
if ($LASTEXITCODE -ne 0) { throw 'test listing failed' }
ctest --test-dir $Build -C Release --output-on-failure
if ($LASTEXITCODE -ne 0) { throw 'tests failed' }
cmake --install $Build --config Release
if ($LASTEXITCODE -ne 0) { throw 'install failed' }
```

这一模板关闭了可选依赖，仅验证基础配置；codec 实验必须另建启用相应依赖的构建，不能复用此结果。源码默认跟调用方工具链的 CRT；MSVC 测不同 CRT 时通过已验证的工具链配置或 `CMAKE_MSVC_RUNTIME_LIBRARY` 明确选择，检查真实编译命令。发布包当前静态 `/MT`、DLL `/MD`，Debug 分别为 `/MTd`、`/MDd`，不要混淆“源码默认”与“发布脚本选择”。

已有定向校准脚本可在**完成相应 build 后**这样调用；以下同样是未来模板。Windows 的 `<构建内可执行文件>` 路径因生成器而异，现有脚本按仓库 CI 的布局寻找，使用不同生成器时先核对，不能盲目判为库回归。

```powershell
# $Source/$Build 是上面已准备好的专用源码/构建目录。
# acp：Windows，LEVELDB_WINDOWS_UTF8_PATHS=OFF，非 UTF-8 系统 ACP。
py -I (Join-Path $Source 'tools/check_compatibility.py') `
    --build $Build --config Release --mode acp
if ($LASTEXITCODE -ne 0) { throw 'ACP calibration failed' }
# utf8：另一个专用源码/构建目录，LEVELDB_WINDOWS_UTF8_PATHS=ON。
# 将 --mode 改为 utf8；不要并发复用上面的源码。
# log-buffer：按仓库 CI 在 Linux 单配置构建运行 --mode log-buffer。
# 用校机可用的 Python 解释器执行同一脚本，保留 -I 和 XML/日志。
```

需要知道静态发布策略是否仍自洽时，可计划执行 `py -I <Source>/tools/release/check.py`；它不会代替真实包构建/消费。实际 release 构建参数按 [`release.yml`](../.github/workflows/release.yml) 和对应脚本的参数定义选取，不把未经核对的命令行写成现成可用工具。

## 10. 哪些兼容值得做：建议先定这些决定

| 决策 | 建议 | 代价或不做的理由 |
| --- | --- | --- |
| 旧调用方路径无需改变 | **建议库默认匹配上游 native code page**，显式保留 UTF-8 变体 | 旧调用方不用改；已有 UTF-8 调用方要继续用对应变体；默认仍有上游字符表达限制 |
| 自动猜 ACP/UTF-8 | **不做** | 无标记字节存在歧义，可能开错/删错库；不能用多试一次保证正确 |
| 合法 Env 自有缓冲区 | **必须兼容** | 这是原公开契约；不应把库整合错误转嫁给调用方 |
| 已有合法数据与实际使用的 codec | **必须匹配目标下游** | 可以交付不同能力包，但不能把缺 decoder 的包称为通用替代品 |
| 跨任意 C++ ABI/CRT | **不承诺**，支持明确组合 | 工具链、运行库、布局和内存所有权有实际边界；提供源码重编路径 |
| 受限目录/不支持目录刷新 | **先定支持范围；有真实需求再做显式降级** | 吞错会降低耐久性；实现可用不等于维持原安全保证 |
| 不完整日志尾部继续复用 | **不保留历史行为** | 保持文件号/数量不值得冒恢复后新写入丢失风险 |
| 损坏输入被宽松读过 | **不恢复不安全行为** | 提供显式救援而不是放松正常读取的内存安全 |
| Repair 全有或全无 | **不承诺** | 上游已有损失可能；应报告可恢复范围及实际损失 |
| 固定错误句子、旧时钟步进、旧文件号 | **一般不兼容偶然细节** | 除非实际下游存在明确依赖；优先维护稳定类别与数据结果 |
| 全部历史发行包继续推荐 | **不建议** | 已知损坏资产应标记并给可靠替代；新代码不能修补已下载的 ZIP |
| 任意 Windows 文件系统/所有 NAS | **不承诺** | 按实际部署逐格验证，不能由 NTFS 结果推导所有网络存储 |
